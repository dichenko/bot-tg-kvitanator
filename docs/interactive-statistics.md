# Интерактивная статистика «Квитанатора»

Ежедневный отчёт и административная команда `/stats` используют один сервис
агрегирования PostgreSQL. В сообщение встроен HTML Widget; отдельного сайта,
Mini App и внешних ресурсов нет.

## Изменения

- `statisticsService.ts`: агрегаты, периоды и текстовая подпись.
- `statisticsWidget.ts`: автономный HTML/CSS/SVG, компактное состояние и проверки
  размеров HTML/zlib/`chat_data`.
- `telegramWidgetApi.ts`: типизированная граница для Bot API 10.4 через `api.raw`
  установленного grammY 1.42.0, включая подписку на `widget_query`.
- `handlers/statistics.ts`, `bot.ts`, `index.ts`: защищённая `/stats`, обработка
  запросов до middleware сессий, подписка на обновления в webhook и polling.
- `dailyStatsService.ts`: сохранённые срезы, блокировка ежедневной доставки,
  восстановление подготовки после перезапуска и текстовый fallback.
- `userService.ts`, `operationService.ts`, TG/MAX callbacks: явная атрибуция каналов.
  В MAX `SENT` теперь выставляется после успешной отправки изображения.
  Ошибка отправки меню после квитанции больше не переводит её в `FAILED` в обоих
  каналах. Повторная отправка квитанции не создаёт новую операцию.
- `config.ts`: проверка корректности `APP_TIMEZONE`.
- Prisma schema и миграция `202611140001_interactive_statistics`.
- `scripts/statistics*.cjs`, `scripts/test-statistics.cjs`, `package.json` и lockfile:
  автоматические проверки, PGlite только как тестовая зависимость.

## Семантика показателей

- **Новые клиенты:** строки `User` по `createdAt`; канал регистрации фиксируется
  при создании пользователя. Два идентификатора у исторического пользователя
  дают `UNKNOWN`, без произвольного выбора платформы.
- **Квитанции:** только `Operation.status = SENT`. Время события — `sentAt`,
  а для исторических `SENT` без этого поля — `createdAt`. Черновики, рендеринг,
  ошибки и удалённые операции не учитываются. Повторная отправка не меняет время.
- **Активные клиенты:** уникальные `userId` среди этих квитанций. По согласованному
  правилу общий итог уникален, TG/MAX показывают присутствие в соответствующем
  канале, «В обоих» показывает пересечение. «Неизвестно» здесь — клиенты, у которых
  за период есть только операции с неизвестным каналом. Поэтому
  `Всего = TG + MAX + Неизвестно − В обоих`.
- Для квитанций и новых клиентов `Всего = TG + MAX + UNKNOWN`.
- Историческое сопоставление людей с разными записями `User` не выполняется.
  Уникальные индексы Telegram/MAX ID уже исключают дубли одного идентификатора.

Интервалы полуоткрытые `[начало, срез)`. День — 24 часа, неделя — 168 часов,
месяц — 720 часов, полгода — минус 6 календарных месяцев в `APP_TIMEZONE`
с корректным ограничением дня месяца. На графике день делится на 6 интервалов
по 4 часа; неделя/месяц — по местным календарным дням; полгода — по местным
месяцам. Первый и последний календарные интервалы могут быть неполными
(например, за полгода обычно видны 7 месячных интервалов).

Все четыре периода вычисляются в одной транзакции `REPEATABLE READ` и сохраняются
в `statistics_reports.snapshot` **до отправки**. Переключатели читают этот JSON;
изменение/удаление исходных операций не меняет уже созданный отчёт. В виджете
только агрегаты, локальные границы интервалов и время среза.

## Миграция и включение

Миграция аддитивная, выполняется в транзакции:

1. Создаёт `StatisticsChannel` и поля `User.registrationChannel`, `Operation.channel`.
2. Восстанавливает TG/MAX только при единственном заполненном идентификаторе;
   оба идентификатора или их отсутствие остаются `UNKNOWN`.
3. Добавляет таблицу отчётов с уникальным ключом ежедневной доставки и индекс
   пользователей по `createdAt`.
4. Создаёт частичный индекс выпущенных квитанций по
   `COALESCE(sentAt, createdAt), channel, userId`. Этот expression index хранится
   в SQL миграции: Prisma schema его не представляет.

Статусы, суммы, номера и даты исторических операций не переписываются.
Backfill и создание индекса берут блокировки таблиц; миграцию следует включать
в обычное окно обновления. До запуска нового кода нужно применить миграцию и
сгенерировать Prisma Client:

```sh
pnpm prisma:migrate:deploy
pnpm prisma:generate
pnpm build
```

На рабочей базе эта миграция в ходе разработки **не применялась**. Production
не разворачивался, настоящие Telegram/MAX API в тестах не вызывались.

Настройки сохранены: `DAILY_STATS_TELEGRAM_ID`, `DAILY_STATS_HOUR`, `APP_TIMEZONE`.
По умолчанию — ежедневно в **07:00 Europe/Moscow**. Планировщик проверяет срок
на границах минут; при обычном запуске немедленный тестовый отчёт не отправляется.
После перезапуска подхватывается пропущенная доставка **текущей местной даты**,
на ближайшем минутном тике. Срез такого отчёта остаётся запланированным временем.
Отчёты за предыдущие пропущенные даты автоматически не рассылаются.

## Доставка и ограничения

Уникальный `deliveryKey` и атомарная аренда подготовки предотвращают параллельную
рассылку несколькими экземплярами. Аренда подготовки истекает через 2 минуты.
Перед внешним API сохраняется `SENDING`; успешные состояния — `SENT`/`FALLBACK`.
Перезапуск во время незавершённого `SENDING` переводит просроченную запись в
`UNCERTAIN` и пишет ошибку в лог; повторной автоматической отправки нет.

У Telegram нет ключа идемпотентности отправки, поэтому абсолютная гарантия
«ровно один раз» при потере ответа API невозможна. При ошибке `sendWidget`
отправляется текст с теми же числами. При сетевом таймауте принятый Telegram
виджет и резервный текст теоретически могут прийти оба; это помечается
`ambiguous: true` в логе. При сбое процесса после отправки следует проверить
чат перед ручной повторной отправкой через `/stats`.

Переключение доступно только настроенному администратору в личном чате и только
для сохранённого `message_id`. Инлайн-сообщения и запросы из других чатов
отвергаются. Между экземплярами редактирование координируется advisory lock.
Ревизии состояния защищают интерфейс от запоздавших ответов. Интерфейс блокирует
повторные нажатия во время запроса и ограничивает их до 5 за 5 секунд; общий
лимит пользователя по всем виджетам также обеспечивает Telegram.

Работа запроса ограничена 8 секундами, затем остаётся до 3 секунд на ответ
`answerWidgetQuery`; запоздавшее редактирование отменяется AbortSignal.
Ошибки редактирования показываются внутри виджета, новых сообщений нет.

Размеры проверяются фактически через UTF-8 и zlib уровня 9 перед отправкой.
Состояние использует компактную запись времён и чисел графика в base36.
При превышении 1024 байт состояние отклоняется; начальная отправка переходит
на текст. Текущие размеры можно вывести командой:

```sh
node -e "console.log(require('./apps/bot/dist/services/statisticsWidget').validateWidgetHtml())"
```

В старых клиентах Telegram поддержка Widgets не определяется ботом. Поэтому
три главных числа и разбивка каналов всегда дублируются в текстовой подписи.
При отказе самого Bot API используется обычное текстовое сообщение.

## Проверки

```sh
pnpm test:stats
```

Тесты самостоятельно собирают DB/shared/bot, используют временный PostgreSQL
PGlite в памяти и подменённый транспорт Telegram/MAX. `.env` не загружается.
Для визуальных тестов нужен установленный Playwright Chromium
(`pnpm --filter @receipt-bot/renderer-worker exec playwright install chromium`);
на Windows тесты могут использовать установленный Edge. В ограниченной Windows
песочнице запуск браузера может требовать исполнения тестов вне неё.

Покрытие: миграция и ограничения PostgreSQL, новые TG/MAX пользователи, явный
канал создания операций, порядок отправки квитанций, повторная отправка,
`SENT`/неуспешные статусы, уникальные активные клиенты и пересечение каналов,
неизвестный канал, пустые данные, границы интервалов, DST, високосные даты,
неизменность среза, все периоды/каналы, права доступа и привязка сообщения,
API-ошибки/fallback, параллельная доставка/запросы, перезапуск/аренда,
таймаут недоступной базы, лимиты размеров, запоздавшие ответы.

Браузерная проверка использует ширины 280/320/390/430/600 px в светлой и тёмной
темах, проверяет высоту до 560 px и отсутствие горизонтального переполнения.
Снимки на синтетических данных сохраняются в
`test-results/statistics/light.png` и `dark.png`.

**Ограничение проверки:** браузер с заглушкой `TelegramWidget` не является
нативным QuickJS Widget sandbox. Используемые возможности сверены с
[Widget profile 1](https://core.telegram.org/bots/widgets#what-widgets-support),
но окончательная проверка на реальных iPhone, Android и Telegram Desktop
не выполнялась. Для неё после обновления тестового бота:

1. В личном чате администратора вызвать `/stats`; должно появиться одно сообщение
   с подписью и тремя карточками.
2. Переключить четыре периода и «Все / TG / MAX», нажать несколько точек графика.
   Сообщение должно оставаться тем же, подпись сохраняет дневные числа среза.
3. Проверить обе темы и узкий экран; неизвестный канал отображается серым,
   пересечение активных клиентов — строкой «В обоих».
4. Выпустить новую квитанцию: старый отчёт должен сохранить значения,
   новый `/stats` — отразить изменение.
5. Проверить `/stats` с другого аккаунта: данных и ответного отчёта не будет.
6. На тестовом окружении проверить отсутствие дублей при двух экземплярах
   и перезапуске после планового времени. Утреннюю отправку реальному
   администратору не использовать как тест без его разрешения.

Официальные контракты: [Widgets](https://core.telegram.org/bots/widgets),
[sendWidget](https://core.telegram.org/bots/api#sendwidget),
[answerWidgetQuery](https://core.telegram.org/bots/api#answerwidgetquery),
[editMessageWidgetData](https://core.telegram.org/bots/api#editmessagewidgetdata).

# Автоматический деплой

Каждый пуш в `main` запускает `.github/workflows/deploy.yml`. Пуши в другие
ветки рабочего бота не обновляют. Доступен и ручной запуск: GitHub → Actions →
Deploy → Run workflow → main.

## Настройки GitHub и VPS

Repository Actions secrets:

- `VPS_HOST` — адрес сервера.
- `VPS_USER` — пользователь SSH (`root` на текущем VPS).
- `VPS_SSH_KEY` — отдельный приватный Ed25519-ключ только для этого workflow.
- `VPS_KNOWN_HOSTS` — закреплённый публичный host key сервера для OpenSSH.

Секрет `VPS_PROJECT_PATH` сохранён для совместимости; новый workflow его не
использует. Каталог приложения закреплён в серверной команде:
`/opt/bot-tg-kvitanator`.

Публичная часть deployment key добавлена в `authorized_keys` с ограничениями:

```text
restrict,command="/usr/local/sbin/kvitanator-deploy" ssh-ed25519 ...
```

Этот ключ допускает только `check` и `deploy <40-значный commit SHA>`.
Произвольный shell, PTY, port forwarding и agent forwarding недоступны.
Обычные административные SSH-ключи не изменяются.

Серверный entrypoint устанавливается из `scripts/deploy-entrypoint.sh` в
`/usr/local/sbin/kvitanator-deploy`. При успешном обновлении он обновляет свою
копию для следующих запусков. Начальная установка на новом VPS выполняется
администратором вместе с добавлением публичного deployment key и закреплением
публичного host key в GitHub Secrets.

## Что происходит при пуше

1. GitHub Actions проверяет наличие настроек SSH и строго проверяет host key.
2. Сервер берёт `flock` на `/var/lock/kvitanator-deploy.lock`; параллельные
   запуски не смешивают сборку, миграции и перезапуск.
3. Проверяет чистоту отслеживаемых файлов и ветку `main`, получает `origin/main`
   и обновляет checkout через fast-forward. Локальные изменения не затираются.
4. Если запуск уже вытеснен новым коммитом в `main`, старый коммит пропускается.
   GitHub сохраняет текущий деплой и самый свежий ожидающий запуск; активная
   миграция не отменяется из-за нового пуша.
5. Собирает образы bot/renderer, пока текущие контейнеры продолжают работать.
6. Сохраняет PostgreSQL dump в `/var/backups/kvitanator` с правами только root.
7. Выполняет `prisma migrate deploy`, обновляет bot/renderer без остановки БД.
8. Проверяет `/health` бота и renderer, запрос PostgreSQL из нового контейнера
   и авторизацию Telegram через `getMe` без отправки сообщений. Только после
   этого запуск становится успешным.

Последний успешно развёрнутый SHA записывается в
`/var/lib/kvitanator/deployed-revision`. Резервные копии автоматически не
удаляются. PostgreSQL volumes и файлы квитанций сохраняются.

Health checks используют текущие локальные порты `3000` (bot) и `3001`
(renderer). Если меняется порт или режим HTTP-сервера, нужно одновременно
обновить проверки в `scripts/deploy.sh`.

## Если запуск завершился ошибкой

Открыть Actions → Deploy → неудачный запуск. При ошибке сервера workflow
выводит состояние контейнеров и последние логи bot/renderer. Неуспешный запуск
не помечается успешным после одной только отправки SSH-команды.

- SSH authentication: проверить deployment key в GitHub и соответствующий
  публичный ключ в `authorized_keys`.
- Host key verification: сверить новый host key через доверенное подключение
  к VPS, затем обновить `VPS_KNOWN_HOSTS`.
- Dirty working tree / non-fast-forward: сохранить и разобрать изменения
  на сервере; workflow их самостоятельно не удаляет.
- Build / migration / health: исправить показанную ошибку и повторить workflow
  либо отправить исправление в `main`.

Повторный запуск после потери соединения сначала проверяет актуальность коммита
и снова выполняет идемпотентные миграции. Откат схемы БД автоматически не
выполняется; резервная копия сохраняется для контролируемого восстановления.
